The v2 pair was created 21 Oct through the Content API, not the
Content Template Builder UI: the editor's brace auto-pairing turned a
pasted {{3}} into a malformed placeholder and then counted it as a
fifth variable, refusing to save without a fifth sample. A template
expecting five values when the caller passes four fails on every real
send. The API takes the body as exact JSON and cannot mangle it.

Same four variables, same order as the originals. Only the body text
is longer, which is what Meta's rejection asked for. Nothing in the
code changes when these are approved - only the two SIDs above.

FOUR of six are approved. contractor_movement and site_monitor are
REJECTED and have been since 16 Oct 13:03 -- within minutes of submission,
never pending. Meta's reason, identical for both:

  "This template has too many variables for its length. Reduce the number
   of variables or increase the message length."  (subCode 2388293)

Both carry 4 variables in a short body. The fix is to LENGTHEN the body,
not to change the variable count, because the caller's argument order is
fixed and documented below.

Also found 20 Oct and NOT previously recorded: resident_morning_brief is
category MARKETING, not UTILITY. The claim further down this file that
every template is utility is false for that one. Marketing templates cost
more in India, need marketing opt-in, and are throttled to users who have
not given it.

This file said APPROVED for all six for about an hour on 20 Oct, written
from a verbal confirmation rather than from the per-template detail view.
The Twilio LIST view has now misled three separate times. The only
trustworthy source is the ApprovalRequests API or the detail page.

Original note on the first four:
"WhatsApp approval status: Approved", category Utility, and channel
eligibility includes WhatsApp BUSINESS INITIATED — which is the mode that
matters. User-initiated only works inside the 24-hour window the sandbox
already gives you.

A Content SID is HX + 32 hex = 34 characters. The code checks the SHAPE
and falls back to freeform if it fails (OCT-120), so a mistyped SID
produces a silent freeform send, not an error.


WHERE EACH IS READ, AND THE VARIABLE ORDER
------------------------------------------
Variable order is not negotiable: it is the order the caller passes.
Changing the template without changing the caller breaks the send.

1. WA_TPL_SOS          whatsapp_alerts.WA_TEMPLATES["sos"]
   Resident presses SOS -> security head + committee.

2. WA_TPL_ESCALATION   whatsapp_alerts.WA_TEMPLATES["escalation"]
   An incident not acknowledged inside the window.

3. WA_TPL_BRIEF        whatsapp_alerts.WA_TEMPLATES["brief"]
   Morning brief, 7:35 am, to the committee's nominated number.

4. WA_TPL_VISITOR      visitor_notify.py — its OWN credential path, not
   whatsapp_alerts. Somebody is standing at the gate. OCT-128/OCT-129.

5. WA_TPL_CONTRACTOR   whatsapp_alerts.WA_TEMPLATES["contractor"]
   contractors.py _notify_whatsapp(), added 7 Oct.
   send_alert(to, "contractor", [who, direction, gate, when], body)
       {{1}} who (name, or "name (company)")
       {{2}} IN or OUT
       {{3}} gate
       {{4}} time

6. WA_TPL_MONITOR      site_heartbeat.py — runs on the HOST under cron,
   reads cfg["wa_tpl_monitor"] OR the env var. Not in a container.
   variables=[tag, name, detail, time]
       {{1}} tag, INCLUDING its emoji (the code sends "🔴 BLIND" /
             "🟢 RESTORED") — the template must NOT add its own
       {{2}} site name
       {{3}} what happened
       {{4}} time
   This is the most important one. It alerts the founder, who has no
   reason to have messaged the business, and it only transmits when a
   site is ALREADY DOWN. Without the template, the one message you
   cannot afford to lose is the one that fails — into a cron log.
